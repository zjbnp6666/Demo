# QCamera-Client —— 直播拉流播放器

从流媒体服务器拉流，解封装、解码、音视频同步渲染，支持三档清晰度切换。

> **默认走 HTTP-FLV**（早期版本用 RTMP）。为什么换 —— 见「踩坑记录」里那条**对照实验**，
> 那是这个项目里最有价值的一次排查。

## 功能特性

- 拉流 → 解封装 → 解码 → 渲染（**HTTP-FLV / RTMP 都支持**，改 URL 即可，但见下方注意事项）
- 音视频同步：音频主时钟（播放头），视频落后丢帧 / 超前缓存 / **坏时钟护栏直通**
- 静默断网检测：`interrupt_callback` 3 秒看门狗 + **首包哨兵**（防"刚连上就被自己踢"）
- **音频设备热插拔自适应**（拔耳机自动重锚时钟 + 重建声卡，不用重启）
- 清晰度切换（高清 / 标清 / 流畅三档）
- 音量调节 + 静音、暂停 / 全屏
- 画面缩放三策略（等比 / 拉伸 / 裁剪）
- 分级日志（`logger.h`）

## 架构

```
HTTP-FLV / RTMP 流
   │
   ├─ 解封装 ─┬─ 视频解码 ─ sws(YUV→RGB) ─ 帧队列 ─ 5ms 定时器 ─ 同步判断 ─ 渲染
   │          └─ 音频解码 ─ swr(→S16)   ─ 音频队列 ─ 10ms 定时器 ─ QAudioSink 播放
   │                                                                    │
   └──────────────────── 音频主时钟 ◄────────────────────────────────────┘
                    （QAudioSink::processedUSecs = 播放头）
```

## 设计亮点

### 1. 音频主时钟用「播放头」，不是「帧到达时间」

最容易犯的错：拿最新解码帧的 pts 当时钟。但帧「到达」≠「已播放」，用到达时间会把时钟拨快，
视频永远"晚到"被丢。用 `QAudioSink::processedUSecs()` —— 声卡**真的播到哪了** —— 视频 pts 跟它比才对得上。

> 顺带一个坑：Qt 文档把 `processedUSecs()` 写成"已处理多少音频"，很容易被读成"写进去多少"。
> **它是播放头**（Windows 后端 `qaudiosystem_platform_stream_support.cpp:210` 累加的是
> **consumedFrames**）。验证手法：写 100ms 音频后立刻读 = 0，200ms 后读 = 100000 —— 数的是"取走"。

### 2. 三态同步 + 一道护栏

`streamstart()` 对每一帧分档处理，**不是一个阈值一刀切**：

| 视频 pts − 音频时钟 | 动作 |
|---|---|
| < −100ms | **过期丢**（落后太多，追不上了） |
| > +3ms | **进缓存**，等下一拍再看 |
| 其余 | 直接上屏 |
| **\|差值\| > 60 秒** | **护栏：直通上屏，不做同步** |

**那道护栏是保命的**：音频时钟一旦被顶坏（比如被 FFmpeg 的 `+2³²` 补偿顶成 43 亿），
没有护栏的话每一帧都会落进「过期丢」→ **一帧不剩 → 只有声音、画面黑**。
有了护栏，坏时钟最多让音画不同步，**不会让画面全黑**。

### 3. 断线检测：看门狗 + 哨兵

`interrupt_callback` 里挂一个"距上次成功读包超过 3 秒就报中断"的看门狗。
两个必须配套的细节：

- **必须刷新 `m_lastReadMs`**（在 `init()` 里）：这个回调是挂在 `AVFormatContext` 上的，
  `avformat_open_input` **内部也会查它**。不刷新的话，重连时带着上次连接的过期值进去，
  回调永远返回 1 → **自己把自己的 open 打断** → 死循环连不上。
- **必须加"首包哨兵"**：刚连上、流还没推上来时，3 秒看门狗会把"正常等待"误判成"断供"，
  实测会**连踢 4 次**。加一个 `m_gotFirstPacket`，读到第一个包之前不启用看门狗。

### 4. 生产者-消费者：单解码线程 + 双定时器

`Avdeio` 一个线程干完「拉流 → 解封装 → 音视频双路解码 → 入两个队列」；
主线程一个 **5ms** 定时器取视频帧上屏、一个 **10ms** 定时器取音频喂声卡。
改解码器/参数只动 `Avdeio` 一处，队列用 `QMutex + QWaitCondition` 保线程安全。

> ⚠️ 上屏定时器**原来写的是 30ms**，那是错的 —— 同步逻辑"本 tick 存、下一 tick 上"
> 让**一帧吃 2 个 tick**，30ms × 2 = 60ms → **30fps 的流只能上屏 16fps**。
> 改成 **5ms** 后一帧 10ms ≪ 33ms，立刻跑满。细节见下面「踩坑记录」。

### 5. 音频设备热插拔的「四步自救」

**拔耳机 / 切设备时的连锁反应**：声卡没了 → 旧 `QAudioSink` **不会自己迁到新设备**
（sink 在创建那一刻就绑定了设备）→ `processedUSecs()` 返 0
→ `audioClock = clockBasePts + (0 − procBace)` **整段掉下去，而且永不自愈**。

一个入口 `relatchAudioClock()` 把四件事收口：

```cpp
void Widget::relatchAudioClock()
{
    deio->m_Queue->clear1();                          // ① 清掉上一段流的音频块，别让旧 PTS 混进新流
    au->strat();                                      // ② 重建 sink（新 sink 绑定"当下"的默认设备）
    clockBasePts = 0; procBace = 0; audioClock = 0;   // ③ 三个时钟【一起】归零重锚
    headpst = false; headWait.invalidate();           // ④ 复位"音频就绪"标志
    updateLoading();
}
```

- **谁来触发**：`QMediaDevices::audioOutputsChanged` → `relatchAudioClock()`；**断流重连走同一个入口**。
- **三个时钟必须一起归零** —— 只归零其中一个，时钟会卡在错的位置，越走越偏。
- **重建 sink 时要"先松手再销毁"**（见踩坑里的 use-after-free）。
- **兜底**：重锚会把 `headpst` 打成 `false`，而此时音频还没喂进来 → 每一拍都在丢视频帧 → 黑屏。
  加一个 `headWait` 超时**强行放行**，保证**没有音频轨的流也能出画面**。

> ⚠️ **兜底是有代价的，要知道**：放行之后音频时钟恒为 0，视频帧 pts 恒 `> 0 + 3ms`
> → **每一帧都进"太早"分支**；而缓存分支**不 pop 新帧** → **每 2 个 tick 才推进 1 帧**。
> **⇒ 上屏帧率被钉死在 `1/(2×tick)`** —— 一条"帧率偷偷取决于某个定时器间隔"的隐藏耦合。

### 6. 策略模式做画面缩放 —— 开闭原则

等比 / 拉伸 / 裁剪三种缩放抽象成 `Renderstrategy` 基类 + 三个子类，`VideoWidget` 只认基类。
加新缩放方式不改旧代码。

## 踩坑记录

### ★ 最有价值的一条：rtmp 和 http-flv，钩子和超时**行为完全不同**

**背景**：客户端靠 `interrupt_callback` 的看门狗检测"服务器静默断网"（不发包、也不发 FIN）。
用 rtmp 时，**挂起服务器 20 秒客户端毫无反应**；换成 http-flv，**~3-4 秒就自己重连**。

**做法**：把探针放在**主线程**（QTimer 驱动，**独立于 `av_read_frame` 那个循环**），
逐秒采样两个数：`距上次回调`（回调多久没被叫了）、`距上次读`（多久没读到包）。
挂起服务器 20 秒：

| | **rtmp** | **http-flv** |
|---|---|---|
| 挂起期间 `距上次回调` | **13240ms → 29282ms**（一路单调涨，**和"距上次读"完全相等**） | **20 ~ 120ms**（一直在跳） |
| 回调被调了吗 | ❌ **一次都没有** | ✅ **每 100ms 一次** |
| 3 秒看门狗 | ❌ **失效**（挂 29 秒都没断） | ✅ **~3-4 秒自己重连** |
| `rw_timeout = 3 秒` | ❌ **也没用**（29 秒没断） | ✅ |
| 服务器恢复后 | ❌ **又卡死，回不来** | ✅ **自己回来了** |

**结论**：
- **rtmp 下 `interrupt_callback` 和 `rw_timeout` 实测【都没用】；http-flv 下两个都有用。**
- rtmp 下服务器一静默，客户端会**永久卡死**（不是"断开重连"，是**卡住不动**）——这就是"黑屏"的样子。

> **⚠️ 关于"为什么"：没查清。**
> 读 FFmpeg 源码，这条链每一环都通（回调从 `AVFormatContext` 一路传到内层 TCP 的 `URLContext`，
> `tcp_read` 阻塞时每 100ms 查一次），`rw_timeout` 也能经 `av_opt_copy` 传下去 —— **可实测就是没生效**。
> **所以只能说「实测 rtmp 下不行」，不能说「源码上 rtmp 不生效」** —— 源码上恰恰说得通。

> **★ 采样点的教训**：探针一开始放在 `av_read_frame` **同一个循环**里，
> 循环一阻塞探针就停 —— 打出来的数是**"累计值"**不是**"逐秒值"**，
> 差点把结论读反。**探针必须独立于被测循环。**

### 其它坑

- **阻塞 pop 死锁** —— 断流后消费者阻塞在 `pop()` 上卡死主线程（界面假死）。pop 前先 `isEmpty()` 判空。
- **退出时崩溃：`QDialog` 值成员 + `unique_ptr` 双重所有权**
  两个控件出生时没 parent（`make_unique`），后来 `setLayout()` 把它们 reparent 给了
  `dialogSyst`（对话框是个**值成员**，声明在最靠后 → 析构最先走）。
  于是 `~QDialog` 删一次、`unique_ptr` 又删一次 → **double free → SIGSEGV**。
  **规矩：只要控件会被任何 layout 收编，就绝不能再让 `unique_ptr` 持有它。**
- **重建 `QAudioSink` 时别 delete 它的 `QIODevice`（use-after-free）**：
  `sink->start()` 返回的 `QIODevice` **归 sink 管**。拿 `unique_ptr` 存着，
  重建时「先 `sink.reset()`（销毁了）→ 再 `io.reset()`」→ **对已释放内存再 delete 一次** → `0xc0000005`。
  **平时可能看着没事，音频设备一热插拔（拔耳机）就崩。** 正解：`io` 存**裸指针**（不拥有）。
- **`QImage` 裸指针构造必须 `copy()` 再 free**（引用不拥有内存）。
- **队列满了"丢新"还是"丢老"，差很多**：原来满了直接 `return`（扔掉**新**帧）→ 留着旧内容播、越播越落后。
  直播的正确反应是**丢老帧、跳到直播边**。
  （`tqueue.cpp` 现在视频/音频两处都是 `while(queue.size() >= MAX_SIZE) takeFirst();` —— 丢到不满为止）

  > ⚠️ **但别把 gop_cache 也算进"该丢的旧料"** —— 服务器在你刚连上时吐的那一坨，
  > 是**起播材料**（从最近一个 I 帧开始的包）。没有它，就得干等下一个关键帧才能解码出画面。
  > **那是该留的 —— 也正是「秒开」能成立的原因之一**（见下面秒开那节）。
- **上屏定时器的粒度不能比帧间隔大**：同步逻辑是"本 tick 存、下一 tick 上"，**一帧吃 2 个 tick**。
  定时器 30ms → 一帧 60ms → **30fps 的流只上屏 16fps**。改成 **5ms** 立刻跑满。
- **队列容量 = 延迟，不是"越多越稳"**：音频队列从 10 块加到 40 块，延迟从 ~200ms 涨到 ~663ms（**耳朵听得出来**）。
- **别拿"不同基准的量"相减**：拿音频轴去减视频轴，据此连编了三个错理论，全被实测打回。
  相减之前先问一句：**这两个数，是同一个零点吗？**
- **切流/重连不清零时钟基准** → 视频 pts 领先播放位置，每帧都走缓存，帧率减半像慢放。
- **`sws_getContext` 要等首帧成功后建**（那时才有宽高）。
- **音频包解码失败后要 `unref` + `continue`**，别顺手送进视频解码器。

## 秒开（首帧延迟）实测与优化

> 目标：点「连接」到屏幕出第一帧的耗时。逐环节埋点实测后，真凶锁定 `avformat_find_stream_info`。

### 各环节实测耗时（本地流）

| 环节 | 耗时 |
|------|------|
| `avformat_open_input` | ~4ms |
| `avformat_find_stream_info` | **~194ms（大头）** |
| 视频首帧解码 + sws + 入队 | ~6ms |
| 音频首帧解码 + swr + 写声卡 | ~1ms |
| 同步判断 + 上屏 | ~0（`headpst` 早已就绪） |

**第一帧真正响应约 198ms，其中 `find_stream_info` 占 ~194ms，其余环节合计 <10ms。**

### 优化尝试与结果

| 手段 | 效果 |
|---|---|
| `analyzeduration=50000`（压分析预算） | ✅ 从 ~4s 降到 ~190ms，立竿见影 |
| `probesize=1024`（压嗅探字节） | ❌ 无效，属协议硬开销 |

### 一路排除的「非真凶」

- 不是**等关键帧**：`gop_cache` 生效，视频首帧解码 +6ms 就出
- 不是**被「等音频」扣住**：无音频时视频不吃亏，`headpst` 早就置位
- 不是**互斥锁**：视频走同一队列，~1ms 就出
- 不是**`byteFree` 门**：初始 35280 满，门根本没堵
- 不是**解码 / 渲染慢**：1~6ms 打完

### 结论

`find_stream_info` 的 ~190ms 已接近下限，`analyzeduration` / `probesize` 都压不动。
**想再快得换思路**：客户端预连接、首帧前直接拉关键帧、硬解加速，或接受这一延迟。

### 踩坑：音视频到达顺序不稳定

实测发现包里的音视频到达顺序**每次连接都不同**（有时音频先、有时视频先）。
**不要用单次观测下「谁快谁慢」的结论**，必须用同一基准在单次运行内对比。跨轮比较时间戳，
正是本次排查反复翻车的主因。
